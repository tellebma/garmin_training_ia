## T1 — Migration : rattachement + résultats + RPC

`supabase/migrations/20260824100000_e23_race_view.sql` (additive, expand/contract respecté) :

- `activities.race_goal_id` (FK `race_goals`, `on delete set null`) + `race_tag_source`
  (`auto` | `manual`), index partiel `(user_id, race_goal_id) where race_goal_id is not null` ;
- table `race_results` (PK `race_goal_id`) + RLS propriétaire sur les 4 verbes ;
- trigger `updated_at` si le projet en a déjà un, sinon champ mis à jour par l'action ;
- RPC `set_activity_race` / `clear_activity_race` en `security definer`, `search_path` figé,
  `grant execute to authenticated` **et** `revoke execute … from public, anon`.

Vérifier l'horodatage du nom de fichier : aucune collision avec une migration existante
(piège vécu : deux migrations au même timestamp → la seconde n'est jamais appliquée).

## T2 — Worker : détection et tag

- `worker/src/garmin_sync/coach/race_tagging.py`
  - `race_expected_distance_m(race)` : somme des `legs` (ou distance du leg mono-discipline) ;
  - `match_race_activities(races, activities)` — **pure** : renvoie `{activity_id: race_goal_id}`
    en appliquant date + discipline + volume plausible (60 % de la distance attendue, plancher
    20 min sans distance) ;
  - `apply_race_tags(db, user_id, races, activities)` : n'écrit que les lignes dont
    `race_tag_source` est `auto` ou nul, marque `race_tag_source = 'auto'`.
- Branchement dans `sync.py` après `_sync_activities`, borné à la fenêtre de sync, sans jamais
  faire échouer le sync (try/except + log, comme les autres étapes annexes).
- `worker/src/garmin_sync/coach/backfill_races.py` : point d'entrée `python -m …` sur tout
  l'historique, sur le modèle de `backfill_tss.py`.
- Tests `worker/tests/test_race_tagging.py` : match nominal triathlon multisport, match
  mono-discipline, rejet du footing du matin (volume), rejet d'un sport incompatible, respect
  d'un tag `manual`, course sans `legs`.

## T3 — Front : logique pure de la vue course

`lib/coach/race-analysis.ts` :

- `buildRaceTimeline({ activities, segments })` : segments ordonnés (discipline, durée, distance,
  FC, allure/vitesse, part du temps total) ; transitions issues d'`activity_segments`, ou
  reconstruites par les trous entre activités ;
- `resolveRaceTime({ timeline, results })` : temps retenu (officiel prioritaire) + écart au
  temps visé ;
- `buildRaceDebrief({ race, timeline, elapsed, previous, prep })` : listes `strengths` /
  `improvements` + verdict — pacing par segment vs répartition estimée, dérive FC, coût des
  transitions, écart à l'objectif, comparaison à la course précédente ;
- `summarizePreparation(activities, prepStart, raceDate)` : volume, nombre de séances, semaines.

Tests `tests/unit/coach/race-analysis.test.ts` : chaque branche du débrief, cas dégradés
(aucun segment, une seule activité, pas d'objectif, pas de course précédente).

## T4 — Server actions

- `app/actions/race-tag.ts` : `tagActivityAsRace` (rattache, ou crée le `race_goal` rétroactif
  quand aucune course n'existe à cette date) / `untagActivityRace`. Validation zod, `revalidatePath`.
- `app/actions/race-results.ts` : `saveRaceResults` — zod strict (durées en `hh:mm:ss` ou secondes,
  bornes de rang, URL http(s) uniquement), upsert `race_results`, `revalidatePath`.
- Tests `tests/unit/race/*.test.ts` avec le client Supabase mocké, sur le modèle des actions
  d'onboarding.
