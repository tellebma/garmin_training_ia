# E15.1 — Intégration Strava (OAuth2 + webhook temps réel)

Date : 2026-07-10
Statut : validé par l'owner, prêt pour planification.

## Contexte et objectif

`docs/superpowers/BACKLOG.md` § EPIC E15 décrit le besoin : récupérer les activités des
athlètes plus vite, et couvrir les marques de montre qui ne sont pas Garmin (Suunto,
Coros, Wahoo, Apple Watch…) via leur export natif vers Strava, sans développer une
intégration par marque. Strava est gratuit en usage perso/petit volume (rate limit
100 req/15 min, 1000/jour) et propose un webhook temps réel — pas de polling nécessaire.

**Limite assumée dès le départ** : Strava n'expose pas les métriques de wellness
(sommeil, HRV, FC repos, composition corporelle) dont dépend le calcul Banister/readiness.
Cette intégration couvre uniquement les **activités**. Le wellness non-Garmin reste
hors scope (E15.5).

## Architecture générale

Même partition que l'intégration Garmin existante :

- Le **worker Python** (`garmin_sync`) détient les secrets Strava (`client_secret`,
  `webhook_verify_token`) et parle à l'API Strava. Next.js ne connaît jamais ces secrets.
- **Next.js** redirige l'utilisateur vers Strava pour l'autorisation OAuth, puis relaie
  le `code` reçu au worker via une Server Action authentifiée par le JWT Supabase de
  l'utilisateur (même pattern que `POST /garmin/connect`).
- Le worker expose un **nouvel endpoint webhook public** (`garmin-sync.tellebma.fr/strava/webhook`),
  au même niveau que les endpoints `/garmin/*` déjà exposés.

```
[Strava OAuth]  ◀── redirect ──  [Next.js /profile/strava/callback]  ── Server Action ──▶  [Worker /strava/connect]
                                                                                                    │
[Strava webhook] ── POST ──────────────────────────────────────────────────────────────▶  [Worker /strava/webhook]
                                                                                                    │
                                                                                                    ▼
                                                                              [Supabase: athlete_strava_credentials,
                                                                                          activities (source='strava')]
```

## Modèle de données

### Nouvelle table `athlete_strava_credentials`

Miroir de `garmin_credentials`, une ligne par utilisateur :

```sql
create table public.athlete_strava_credentials (
  user_id uuid primary key references auth.users(id) on delete cascade,
  strava_athlete_id bigint not null unique,
  oauth_tokens_encrypted text not null,
  last_sync_at timestamptz,
  last_sync_status text,
  initial_sync_completed_at timestamptz,
  token_refresh_failed_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

- `oauth_tokens_encrypted` : JSON `{access_token, refresh_token, expires_at}` chiffré
  avec `TokenCipher` (même mécanisme Fernet que Garmin), stocké en `text` directement
  (pas de `bytea`, cf. piège déjà rencontré sur `garmin_credentials`).
- `strava_athlete_id` : clé de résolution `owner_id` (webhook) → `user_id`. Index unique
  car c'est la table de lookup au moment d'un événement webhook.
- RLS : mêmes 4 policies (`select`/`insert`/`update`/`delete` own row) + trigger
  `touch_updated_at`, identique au pattern `garmin_credentials`.

### Généralisation de `activities`

```sql
alter table public.activities
  add column source text not null default 'garmin' check (source in ('garmin', 'strava')),
  add column strava_activity_id bigint,
  alter column garmin_activity_id drop not null;

alter table public.activities
  drop constraint activities_user_id_garmin_activity_id_key; -- nom auto Postgres pour `unique (user_id, garmin_activity_id)`

create unique index activities_user_garmin_uidx
  on public.activities (user_id, garmin_activity_id) where source = 'garmin';

create unique index activities_user_strava_uidx
  on public.activities (user_id, strava_activity_id) where source = 'strava';

alter table public.activities
  add constraint activities_garmin_id_check
    check (source <> 'garmin' or garmin_activity_id is not null),
  add constraint activities_strava_id_check
    check (source <> 'strava' or strava_activity_id is not null);
```

C'est le pas de généralisation « `source` par table » que E15.5 anticipait déjà dans le
backlog — fait ici pour la première fois, à réutiliser telle quelle pour une 3e source
(Polar, E15.5) sans nouvelle migration structurelle.

### `activity_samples` : **non généralisée en V1**

Cette table est aujourd'hui `primary key (user_id, garmin_activity_id, sample_index)`,
strictement Garmin. La généraliser est un changement de clé primaire, un chantier
distinct. **Décision de scope (validée)** : les activités Strava n'auront pas de samples
GPS en V1 — pas de tracé carte, pas de courbes détaillées (FC/allure/altitude dans le
temps) pour ces activités. Elles apparaissent normalement partout ailleurs (historique,
stats, cockpit, TSS/charge). Tracé comme item « Suite » dans `BACKLOG.md`.

## Connexion (OAuth Authorization Code)

1. Carte "Strava" sur `/profile`, miroir de la carte Garmin existante (voir
   `app/(app)/profile/page.tsx` section "Garmin Connect"). État non connecté : lien
   "Connecter Strava". État connecté : date de dernière sync + bouton déconnexion.
2. Le lien pointe vers :
   `https://www.strava.com/oauth/authorize?client_id=<NEXT_PUBLIC_STRAVA_CLIENT_ID>&response_type=code&redirect_uri=<APP_URL>/profile/strava/callback&scope=activity:read_all&state=<random>`.
   Le `state` est généré côté serveur, posé dans un cookie `httpOnly` de courte durée,
   et vérifié au retour (protection CSRF standard OAuth).
3. Nouvelle route `app/(app)/profile/strava/callback/page.tsx` (protégée par
   `requireOnboarded`) : lit `code`/`state` en query params, vérifie le `state` contre
   le cookie, puis appelle une Server Action `connectStrava(code)`.
4. `connectStrava` fait `POST /strava/connect` sur le worker avec `{code}`, JWT
   utilisateur en `Authorization` (comme `garmin_connect`). Le worker :
   - échange `code` contre `{access_token, refresh_token, expires_at, athlete}` via
     `POST https://www.strava.com/oauth/token` (avec `client_id`/`client_secret`
     worker-only) ;
   - chiffre et upsert la ligne `athlete_strava_credentials` (`strava_athlete_id` vient
     de `athlete.id` dans la réponse) ;
   - lance un **backfill initial en thread daemon** (mêmes 90 jours que le pattern
     Garmin `_trigger_initial_sync`, voir `worker/src/garmin_sync/connect.py`), retour
     HTTP immédiat `{"status": "connected"}`.
5. La page callback redirige vers `/profile?strava=connected` (ou `?strava=error`),
   affichage d'un toast/bandeau de confirmation.
6. **Déconnexion** : bouton sur `/profile` → Server Action qui supprime directement la
   ligne `athlete_strava_credentials` via le client Supabase (RLS `delete own row`
   suffit, pas besoin de passer par le worker). Best-effort : révoquer aussi le token
   côté Strava via `POST /oauth/deauthorize` avant la suppression, sans bloquer la
   déconnexion locale si cet appel échoue.

## Dédup Garmin/Strava (décision produit validée)

Beaucoup d'athlètes ont Garmin → export automatique vers Strava. Si les deux sources
sont connectées, la même activité physique peut arriver deux fois. Règle V1 : **Garmin
prioritaire**. Avant d'insérer une activité `source='strava'`, on vérifie s'il existe déjà
une activité `source='garmin'` pour ce `user_id` avec un `start_time` à ±5 minutes et le
même `sport` normalisé — si oui, l'activité Strava est **ignorée silencieusement** (pas
d'erreur, pas de ligne créée). Implémenté comme une fonction pure testable,
`is_likely_garmin_duplicate(db, user_id, start_time, sport) -> bool`, appelée depuis le
point d'insertion Strava (backfill et webhook).

## Webhook temps réel

### Souscription (une seule par application, pas par utilisateur)

Strava n'autorise qu'une seule souscription webhook active par application. Sa création
est une **action ops one-shot**, à exécuter par l'owner une fois les secrets en place
(voir « Setup manuel owner » ci-dessous) — je ne peux pas créer l'app Strava ni la
souscription à sa place, ça nécessite un compte Strava et les vrais secrets client.

### Endpoints worker

- `GET /strava/webhook` : validation de souscription. Répond
  `{"hub.challenge": "<valeur>"}` si `hub.verify_token` (query param) correspond à
  `STRAVA_WEBHOOK_VERIFY_TOKEN` (secret worker), sinon 403.
- `POST /strava/webhook` : payload Strava standard
  `{object_type, object_id, aspect_type, owner_id, subscription_id, event_time, updates}`.
  - Retour HTTP 200 quasi immédiat (Strava exige un ACK sous 2s) — traitement métier
    lancé dans un thread daemon, même pattern que `_trigger_initial_sync`.
  - Résolution `owner_id` (Strava athlete id) → `user_id` via
    `athlete_strava_credentials.strava_athlete_id`. Si inconnu (désync, souscription
    d'un autre environnement), on logue et on ignore.
  - `object_type == 'activity'` uniquement (Strava peut aussi notifier des events
    `athlete`, ex. désautorisation) :
    - `aspect_type in ('create', 'update')` → `GET /activities/{object_id}` avec le
      token de l'utilisateur (rafraîchi si expiré, voir ci-dessous), transformation,
      upsert avec la règle de dédup.
    - `aspect_type == 'delete'` → suppression de la ligne
      `activities` correspondante (`source='strava' and strava_activity_id=object_id`).
  - `object_type == 'athlete'` et `updates.authorized == "false"` (l'utilisateur a
    révoqué l'accès depuis Strava) → efface `athlete_strava_credentials` pour ce
    `strava_athlete_id`.
  - Toute exception dans le thread est capturée et loguée (jamais de crash worker),
    même discipline que `_trigger_initial_sync`.

### Rafraîchissement de token

Les access tokens Strava expirent après 6h. `_get_valid_access_token(user_id)` lit
`expires_at` depuis le blob déchiffré ; si expiré (ou expire dans <60s), appelle
`POST /oauth/token` avec `grant_type=refresh_token`, persiste les nouveaux tokens
(Strava peut faire tourner le `refresh_token` aussi). En cas d'échec de refresh :
`token_refresh_failed_at` posé (même sémantique que Garmin), le webhook/backfill
abandonne silencieusement pour cet utilisateur jusqu'à reconnexion.

### Rate limiting

100 req/15 min et 1000/jour, partagés par **toute l'application** (tous les
utilisateurs). Un compteur en mémoire suffit pour la V1 (mono-instance worker, même
limite pragmatique que les cooldowns Garmin `connect.py`) : si le budget 15 minutes est
épuisé, les traitements webhook/backfill en attente sont reportés (retry léger avec
backoff), jamais perdus silencieusement — au pire, le prochain event webhook ou un rerun
de backfill les rattrape.

## Transformer

`worker/src/garmin_sync/transformers/strava_activities.py` : fonction pure
`transform_strava_activity(raw: dict) -> dict` mappant vers les mêmes colonnes que le
transformer Garmin (`duration_s`, `distance_m`, `hr_avg/max`, `power_avg/max`,
`pace_avg_s_per_km`, `elevation_gain_m`, `calories`), plus `source='strava'` et
`strava_activity_id`. `raw` stocke le payload Strava brut (comme Garmin). Le mapping de
sport Strava (`type`/`sport_type`) vers les 5 sports canoniques (swim/bike/run/brick/race)
réutilise la même logique de normalisation que `_normalize_sport` côté Garmin (passthrough
si type inconnu, cf. item backlog « Activités hors triathlon »). `tss` : non calculable
depuis les champs Strava de base en V1 — laissé `null` (le reste du coach gère déjà les
TSS nuls).

## Setup manuel owner (hors repo, avant que ça marche en prod)

1. Créer une application sur `https://www.strava.com/settings/api` : obtenir
   `client_id`/`client_secret`. « Authorization Callback Domain » = domaine apex
   `garmin-training-ia.vercel.app` (Strava n'accepte qu'un domaine, sans chemin/scheme).
2. Secrets worker (`.env` local + `docker-compose.prod.yml`/UNRAID) : `STRAVA_CLIENT_ID`,
   `STRAVA_CLIENT_SECRET`, `STRAVA_WEBHOOK_VERIFY_TOKEN` (valeur aléatoire générée une
   fois).
3. Secret/var Vercel : `NEXT_PUBLIC_STRAVA_CLIENT_ID` (le client_id est public, utilisé
   pour construire l'URL d'autorisation côté navigateur), `STRAVA_REDIRECT_URI` si besoin
   d'un override par environnement (preview vs prod).
4. Après déploiement du worker avec les secrets, créer la souscription webhook une
   fois (commande exacte fournie dans le plan d'implémentation) :
   `POST https://www.strava.com/api/v3/push_subscriptions` avec `client_id`,
   `client_secret`, `callback_url=https://garmin-sync.tellebma.fr/strava/webhook`,
   `verify_token=<STRAVA_WEBHOOK_VERIFY_TOKEN>`.

## Tests

- Worker (pytest) : `transform_strava_activity` (mapping, sports inconnus, valeurs
  nulles), `is_likely_garmin_duplicate` (fenêtre temporelle, sport différent, aucune
  activité Garmin), flow `connect` (échange code, upsert credentials, mock HTTP Strava),
  `GET/POST /strava/webhook` (echo challenge, `owner_id` inconnu, create/update/delete,
  désautorisation, refresh token expiré/échoué, rate limit dépassé).
- Frontend (Vitest) : carte Strava sur `/profile` (états connecté/non connecté/erreur
  refresh), route callback (state CSRF valide/invalide, redirection succès/erreur),
  Server Action `connectStrava`.
- Migration : vérifier que les deux index uniques partiels empêchent bien les doublons
  par source sans bloquer l'insertion croisée (un `user_id` peut avoir une ligne Garmin
  et une ligne Strava au même `start_time` si la dédup ne matche pas — comportement
  attendu, pas un bug).
