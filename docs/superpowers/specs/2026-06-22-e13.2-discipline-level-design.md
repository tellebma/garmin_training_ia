# E13.2 — Croiser le niveau déclaré par discipline avec l'historique réel

**Date** : 2026-06-22
**EPIC** : E13 — Plan d'entraînement réaliste et individualisé
**Statut** : design validé, prêt pour plan d'implémentation
**Priorité** : P0

## Contexte

Le niveau par discipline (`athlete_profiles.sports_strengths`, jsonb `{swim,bike,run}` ∈ 1-5)
est saisi à l'onboarding et **déjà branché sur le moteur** (modulation de la répartition de
TSS via `distribute_weekly_tss_by_sport`, bornage de l'intensité via
`pick_session_types_for_phase(max_level=...)`, prompt OpenAI). Le reliquat E13.2 est de
**confirmer ou affiner ce niveau déclaré à l'aide de l'historique réel d'activités**, qui est
aujourd'hui purement déclaratif : un athlète qui s'entraîne beaucoup et régulièrement dans une
discipline qu'il a déclarée faible devrait voir cette discipline réévaluée, et inversement.

## Objectif

À partir des 90 derniers jours d'activités, dériver un **niveau observé** par discipline,
le réconcilier avec le niveau déclaré pour produire un **niveau effectif borné**, et exposer
la divergence (+ sa raison) à l'athlète.

Décisions de cadrage validées :

1. **Ambition** : signal de divergence **et** ajustement borné du niveau effectif (±1 cran max).
2. **Signaux** : volume + régularité + charge soutenue par discipline. Pas d'allure/puissance
   absolue (trop fragile sans benchmark). On détecte une **incohérence relative** déclaré↔observé,
   on ne recalcule pas un niveau absolu.
3. **Sens d'ajustement** : montée **et** descente, mais la descente n'est autorisée que si les
   données de la discipline sont suffisantes (l'absence de données ≠ faiblesse — ex. natation
   non trackée en piscine ne doit jamais faire baisser le niveau natation).
4. **Exposition UI** : page `/profile`, à côté des niveaux déclarés.

## Architecture (approche retenue : module pur + calcul à la volée)

Pas de persistance : le niveau effectif et la divergence sont recalculés à la demande (90 j
d'activités = calcul léger). Zéro migration, jamais de cache obsolète. Si la perf l'exige un
jour, un cache pourra être ajouté ultérieurement (comme pour le briefing).

### Composants

**`worker/src/garmin_sync/coach/sports.py`** (nouveau, petit) — factorise le mapping
sport→discipline aujourd'hui dupliqué dans `session_feedback.py` :

- `DISCIPLINE_SPORTS: dict[str, set[str]]` — swim/bike/run → variantes Garmin
  (`running`, `trail_running`, `cycling`, `indoor_cycling`, `lap_swimming`, …).
- `normalize_discipline(sport: str) -> str | None` — renvoie `"swim"|"bike"|"run"` ou `None`.
- `session_feedback.py` est mis à jour pour importer ce mapping (DRY, pas de refacto hors-scope).

**`worker/src/garmin_sync/coach/discipline_level.py`** (nouveau, cœur) — **fonction pure**,
aucun accès DB :

```python
compute_discipline_levels(
    declared: dict[str, int],
    activities: list[dict],
    today: date | None = None,
) -> DisciplineLevels
```

`DisciplineLevels` est un dataclass frozen exposant :
- `disciplines: dict[str, DisciplineLevel]` (par discipline déclarée)
- `effective_strengths: dict[str, int]` (consommé par le planner)
- `to_dict()` (forme JSON pour l'endpoint / l'UI)

**`worker/src/garmin_sync/coach/planner.py`** — branchement minimal :
- `_load_today_banister_state` retourne désormais aussi les rows d'activités chargées (évite une
  2e requête).
- `generate_plan` calcule `effective_strengths = compute_discipline_levels(...).effective_strengths`
  et le passe à `_build_week_sessions` à la place de `sports_strengths` brut.

**`worker/src/garmin_sync/main.py`** — nouvel endpoint `POST /coach/discipline-levels`
(JWT user, même garde que les autres endpoints coach) : charge profil + activités 90 j, renvoie
`compute_discipline_levels(...).to_dict()`.

**Frontend `/profile`** — encart par discipline affichant le niveau retenu, un badge d'ajustement
(↑ / ↓ / =), et la raison, à côté des niveaux déclarés. Données récupérées via le client worker.

## Règles déterministes

Signaux calculés par discipline sur **90 jours** (`WINDOW_DAYS = 90`) :

- `activities_90d` : nombre d'activités de la discipline.
- `sessions_per_week` : `activities_90d / (WINDOW_DAYS / 7)`.
- `sustained` : la discipline est active dans **≥ 2 des 3 sous-fenêtres de 30 j** (évite qu'un
  burst concentré compte comme régularité soutenue).
- `tss_share` : part de TSS de la discipline / TSS total des disciplines déclarées (informatif).

Confiance :

- `confident = activities_90d >= MIN_ACTIVITIES_CONFIDENT` (`MIN_ACTIVITIES_CONFIDENT = 6`,
  ≈ 1 séance / 2 semaines sur 90 j).
- Si non confident → **aucun ajustement**, `confidence = "low"`.

Ajustement (plafond 5, plancher 1, `STRONG_REGULARITY = 2.0`, `WEAK_REGULARITY = 0.5`) :

- **Montée +1** si `declared <= 2` ET `confident` ET `sessions_per_week >= STRONG_REGULARITY`
  ET `sustained`.
  Raison : « {Discipline} remonté à {effective} : entraînement régulier et soutenu
  (~{sessions_per_week}/sem sur 90 j) au-dessus du niveau déclaré. »
- **Descente −1** si `declared >= 4` ET `confident` ET `sessions_per_week <= WEAK_REGULARITY`.
  Raison : « {Discipline} ajusté à {effective} : peu d'entraînement observé sur 90 j malgré un
  niveau déclaré élevé. »
- Sinon `effective = declared`, `adjustment = 0`. Raison « Niveau confirmé » si `confident`,
  sinon « Données insuffisantes pour confirmer ».

Toutes les bornes sont des constantes nommées en tête de `discipline_level.py`, faciles à régler
et à tester.

## Structure de données

```jsonc
{
  "disciplines": {
    "swim": {
      "declared": 2, "effective": 2, "adjustment": 0,
      "confidence": "low",
      "reason": "Données insuffisantes pour confirmer.",
      "signals": {"activities_90d": 1, "sessions_per_week": 0.1, "sustained": false, "tss_share": 0.04}
    },
    "bike": {
      "declared": 3, "effective": 4, "adjustment": 1,
      "confidence": "high",
      "reason": "Vélo remonté à 4 : entraînement régulier et soutenu (~2,4/sem sur 90 j) au-dessus du niveau déclaré.",
      "signals": {"activities_90d": 22, "sessions_per_week": 2.4, "sustained": true, "tss_share": 0.55}
    },
    "run": {
      "declared": 4, "effective": 4, "adjustment": 0,
      "confidence": "high",
      "reason": "Niveau confirmé.",
      "signals": {"activities_90d": 14, "sessions_per_week": 1.5, "sustained": true, "tss_share": 0.41}
    }
  }
}
```

`effective_strengths` (interne, non sérialisé dans l'endpoint mais dérivable) :
`{"swim": 2, "bike": 4, "run": 4}`.

## Data flow

1. `generate_plan` charge profil + activités (via `_load_today_banister_state` étendu).
2. `compute_discipline_levels(declared, activities)` → `effective_strengths`.
3. `effective_strengths` injecté dans `_build_week_sessions` (répartition TSS + intensité).
4. `/coach/discipline-levels` charge profil + activités 90 j, renvoie l'objet complet.
5. `/profile` appelle l'endpoint et affiche l'encart par discipline.

## Gestion des erreurs / cas limites

- Aucune activité → toutes les disciplines `confidence = "low"`, `effective = declared` (no-op
  sûr). Le planner reste fonctionnel sans historique.
- Discipline absente de `sports_strengths` → défaut 3 (cohérent avec le planner actuel).
- Sports Garmin non mappés → ignorés (ne polluent aucune discipline).
- L'endpoint suit le pattern d'erreur worker existant (`{status, error_id, type}`).
