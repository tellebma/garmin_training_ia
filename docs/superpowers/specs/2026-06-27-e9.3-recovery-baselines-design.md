# E9.3 — Récupération individualisée (baselines personnelles)

**Date** : 2026-06-27
**EPIC** : E9 — Cockpit de performance et suivi longitudinal
**Statut** : Spec validée (design approuvé)
**Priorité** : P1

## Contexte et objectif

Le briefing quotidien (`briefing.py`) calcule déjà un `readiness_score` à partir de la
HRV, du sommeil, de la FC repos et de la Body Battery, mais en grande partie sur des
**seuils absolus** (sauf la FC repos, déjà comparée à une médiane 30 j). E9.3 introduit
des **baselines personnelles** pour les 5 signaux de récupération, leurs **tendances**,
et une notion de **confiance** et de **fraîcheur** des données — exposées dans le cockpit
`/stats` et réutilisées par le briefing.

Garde-fou produit (rappel backlog) : aucune métrique isolée ne doit être présentée comme
un diagnostic ou une prédiction de blessure. L'affichage reste prudent et indique les
données absentes ou insuffisantes.

## Décisions de design (validées)

1. **Module unique côté worker, matérialisé** (pattern E7 Banister) : `recovery_baselines.py`
   est la source de vérité ; recalculé au sync ; écrit dans une table `recovery_baselines`.
2. Le **briefing** lit la table (rebranché sur les baselines perso) ; le **front `/stats`**
   lit la table directement (server component).
3. **Méthode uniforme** : baseline = médiane glissante 28 j ; valeur récente = médiane 7 j ;
   tendance = écart relatif orienté physiologiquement ; confiance = couverture de données.
4. **Livrable V1 complet** : module + table + panneau cockpit + rebranchement briefing.

## Métriques et orientation

| Métrique | Source | Colonne | « Mieux » = |
|---|---|---|---|
| HRV (rMSSD) | `hrv` | `hrv_rmssd` | ↑ plus haut |
| FC repos | `daily_metrics` | `resting_hr` | ↓ plus bas |
| Sommeil | `sleep` | `sleep_duration_s` + `sleep_score` | ↑ plus haut |
| Stress moyen | `daily_metrics` | `stress_avg` | ↓ plus bas |
| Body Battery | `daily_metrics` | `body_battery_high` | ↑ plus haut |

## Architecture

```
Sync quotidien (cron.py, après recompute_daily_state)
        │
        ▼
recompute_recovery_baselines(user_id)        [recovery_baselines.py]
        │  lit hrv / sleep / daily_metrics sur 28 j (une passe)
        ▼
  table recovery_baselines  (1 ligne / user, upsert)
        ├─→ briefing.py        (lit la table, remplace les seuils absolus)
        └─→ /stats RecoveryPanel (front lit la table en direct)
```

## Module de calcul

`worker/src/garmin_sync/coach/recovery_baselines.py` — fonctions pures + orchestrateur.

### Fonction pure (par métrique)

```python
WINDOW_DAYS = 28
RECENT_DAYS = 7
STABLE_THRESHOLD = 0.05  # ±5 % d'écart relatif = stable

# confiance par nombre de jours couverts dans la fenêtre 28 j
CONFIDENCE_HIGH = 21      # >= 21 jours -> high
CONFIDENCE_MEDIUM = 10    # 10..20 -> medium ; < 10 -> low

FRESHNESS_MAX_AGE_DAYS = 2  # dernière donnée <= 2 j -> fresh, sinon stale

def compute_metric_baseline(
    samples: list[tuple[date, float]],   # (date, valeur) non triées, valeurs non nulles
    *,
    today: date,
    higher_is_better: bool,
) -> MetricBaseline
```

`MetricBaseline` (TypedDict, contrat figé, identique en Python et TS) :

```python
class MetricBaseline(TypedDict):
    baseline: float | None        # médiane 28 j (None si aucune donnée)
    recent: float | None          # médiane 7 j
    trend: Literal["improving", "stable", "declining", "no_data"]
    confidence: Literal["high", "medium", "low", "no_data"]
    freshness: Literal["fresh", "stale", "no_data"]
    days_covered: int             # nb de jours avec donnée dans la fenêtre 28 j
    last_date: str | None         # ISO date de la dernière donnée
```

Règles :
- `baseline` = médiane des valeurs sur 28 j ; `recent` = médiane sur 7 j.
- **tendance** : `delta = (recent - baseline) / baseline`. Si `|delta| <= STABLE_THRESHOLD`
  ou `baseline <= 0` → `stable`. Sinon, orientée : si `higher_is_better`, `delta > 0` →
  `improving`, sinon `declining` ; si `not higher_is_better`, on inverse. Si `recent` ou
  `baseline` absent → `no_data`.
- **confiance** : par `days_covered` (≥21 high, 10–20 medium, <10 low). `0` → `no_data`.
- **fraîcheur** : `today - last_date <= 2 j` → `fresh`, sinon `stale` ; pas de donnée → `no_data`.
- Aucune donnée → tous les champs `None`/`no_data`, **jamais d'exception**.

### Sommeil (deux sous-signaux)

Le sommeil combine durée et score. On calcule **un** `MetricBaseline` sur un indice
normalisé 0–100 pour la tendance, mais on stocke aussi les deux valeurs brutes pour
l'affichage :

```python
class SleepBaseline(MetricBaseline):
    duration_baseline_s: int | None
    duration_recent_s: int | None
    score_baseline: int | None
    score_recent: int | None
```

Indice sommeil = moyenne de (score/100) et (durée normalisée par un plafond de 8 h, clampé
à 1.0), ×100. `higher_is_better = True`.

### Orchestrateur

```python
def recompute_recovery_baselines(user_id: str) -> None
```

1. charge 28 j de `hrv` (`date, hrv_rmssd`), `sleep` (`date, sleep_duration_s, sleep_score`),
   `daily_metrics` (`date, resting_hr, stress_avg, body_battery_high`) — en lecture
   service-role ;
2. calcule les 5 baselines (`hrv`, `resting_hr`, `sleep`, `stress`, `body_battery`) ;
3. upsert une ligne dans `recovery_baselines` (`on_conflict=user_id`), avec `computed_at`
   et `raw_meta` (fenêtre, jours couverts par métrique).
4. **Ne lève jamais** : un échec est loggé et avalé (comme `recompute_daily_state`).
   Appelé dans `cron.run_sync_for_user`, juste après `recompute_daily_state`.

## Table `recovery_baselines`

```sql
create table if not exists public.recovery_baselines (
  user_id uuid primary key references auth.users(id) on delete cascade,
  computed_at timestamptz not null default now(),
  hrv jsonb,
  resting_hr jsonb,
  sleep jsonb,
  stress jsonb,
  body_battery jsonb,
  raw_meta jsonb not null default '{}'::jsonb,
  created_at timestamptz not null default now()
);

alter table public.recovery_baselines enable row level security;

create policy "recovery_baselines_select_own"
  on public.recovery_baselines for select
  using (auth.uid() = user_id);
-- pas de policy insert/update/delete : seul le worker (service_role) écrit.
```

Chaque colonne jsonb porte un `MetricBaseline` (ou `SleepBaseline` pour `sleep`). Le choix
jsonb-par-métrique donne une structure homogène, évolutive sans migration, mappée
directement par le front. Le contrat est figé par `MetricBaseline` (Python) + un type TS
miroir.

Migration auto-appliquée via la CI E17 au merge sur `main`.

## Consommation

### Briefing (`briefing.py`)

- Lit `recovery_baselines` pour l'utilisateur (une requête), au lieu de recalculer.
- `_score_resting_hr` : utilise `resting_hr.baseline` de la table (remplace
  `_load_resting_hr_baseline`, qui peut être supprimée).
- `_score_sleep`, `_score_body_battery` : comparent à la baseline perso plutôt qu'à des
  seuils absolus ; on garde un repli sur les seuils absolus quand `confidence == "low"`
  (pas assez d'historique pour une baseline fiable).
- `_score_stress` : **nouveau** facteur, basé sur la baseline stress.
- Le `readiness_score`, son échelle et le format de sortie JSON **restent inchangés**
  (rétrocompat des consommateurs `/today`). Si la table est absente (premier sync pas
  encore passé), le briefing retombe sur son comportement actuel (seuils absolus).

### Panneau cockpit `/stats`

- `lib/dashboard/recovery.ts` : type TS miroir de `MetricBaseline`/`SleepBaseline` + un
  loader qui lit `recovery_baselines` via le client Supabase server (comme
  `performance-cockpit.ts`).
- `RecoveryPanel` (server component) : une carte par métrique avec
  - la valeur récente + une flèche de tendance **orientée** (↑ vert = mieux, → gris,
    ↓ rouge = moins bien) ;
  - un libellé prudent (« HRV au-dessus de ta moyenne », jamais « tu es fatigué ») ;
  - un badge confiance/fraîcheur : « données insuffisantes » si `low`/`no_data`,
    « donnée ancienne » si `stale`.
- Pas d'emoji ; libellés FR accentués.

## Gestion des erreurs

| Cas | Comportement |
|---|---|
| Aucune donnée pour une métrique | `MetricBaseline` tout `no_data` ; carte « données insuffisantes ». |
| Baseline ≤ 0 ou division impossible | tendance `stable`. |
| Table absente (1er sync non passé) | briefing : repli seuils absolus ; panneau : état vide « bientôt disponible ». |
| Échec du recompute au sync | loggé et avalé ; n'interrompt pas le sync. |

## Plan de tests

**Worker (`recovery_baselines.py`)**
- `compute_metric_baseline` : médiane correcte ; tendance improving/stable/declining selon
  orientation (HRV ↑ vs RHR ↓) ; seuil ±5 % ; confiance par couverture (≥21 / 10–20 / <10) ;
  fraîcheur (≤2 j vs plus ancien) ; aucune donnée → `no_data` sans exception ; baseline ≤ 0
  → stable.
- Sommeil : indice combiné durée+score ; valeurs brutes stockées.
- `recompute_recovery_baselines` : upsert d'une ligne avec les 5 métriques (DB mockée) ;
  avale les exceptions.

**Briefing**
- Rebranchement : `readiness_score` et le format de sortie inchangés sur un cas de
  référence ; repli sur seuils absolus quand la table est absente ou `confidence == low`.
- `_score_stress` : nouveau facteur produit le bon `ReadinessFactor`.

**Frontend**
- Loader `recovery.ts` : mappe la ligne en types ; gère la table absente.
- `RecoveryPanel` : rend les cartes, la flèche orientée, les badges confiance/fraîcheur ;
  état « données insuffisantes ».

## Hors scope (YAGNI)

- Pas de graphiques temporels de récupération (relève d'E14.1).
- Pas de score de récupération composite unique (on expose les 5 signaux séparément ;
  le `readiness_score` du briefing reste la synthèse côté décision).
- Pas de prédiction ni d'alerte blessure (garde-fou produit).
- Pas de recalcul on-demand : la matérialisation au sync suffit (1 sync/jour minimum).

## Critères d'acceptation

1. Après un sync, `recovery_baselines` contient une ligne par user avec les 5 métriques
   renseignées (ou `no_data` si l'historique manque).
2. Le panneau `/stats` affiche, par métrique, valeur récente + tendance orientée +
   confiance/fraîcheur, en langage prudent, sans emoji.
3. Le briefing utilise les baselines perso pour HRV/RHR/sommeil/stress/Body Battery, avec
   repli sur seuils absolus en l'absence de baseline fiable ; `readiness_score` et format
   de sortie inchangés.
4. Aucune métrique n'est présentée comme un diagnostic ; les données insuffisantes ou
   anciennes sont signalées.
5. Tous les quality gates passent (worker pytest/ruff/mypy, front lint/typecheck/test,
   SonarQube, coverage).
