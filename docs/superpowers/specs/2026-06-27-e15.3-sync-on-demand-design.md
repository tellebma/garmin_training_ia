# E15.3 — Sync on-demand avec garde-fou anti-spam

**Date** : 2026-06-27
**EPIC** : E15 — Ingestion multi-source et quasi temps réel
**Statut** : Spec validée (design approuvé)
**Priorité** : P1

## Contexte et objectif

Aujourd'hui les activités Garmin n'arrivent dans l'app que via le cron (3 passes/jour),
soit une latence pouvant atteindre ~8h. L'objectif d'E15.3 est de réduire la **latence
perçue** en déclenchant une sync légère quand l'utilisateur sollicite l'app, sans
augmenter le risque de rate-limit / ban IP côté Garmin (piège connu : `python-garminconnect`
est rate-limité agressivement, 429 → ban 1-24h).

Ce n'est pas du « push temps réel » (réservé à Strava webhooks / Garmin officiel,
voir E15.1 / E15.2) : c'est un **pull au geste**, bridé par un garde-fou.

## Décisions de design (validées)

1. **Garde-fou côté worker**, juste devant l'API Garmin — protège la ressource quel que
   soit l'appelant.
2. **Mécanisme = 1 colonne + UPDATE conditionnel atomique** (pas de nouvelle table),
   réutilise l'idiome de rate-limiting déjà présent dans le projet.
3. **Sync `activities_only` (delta 2 jours) en thread daemon** — léger, rapide, réponse
   immédiate ; réutilise `run_sync_for_user`.
4. **Déclencheurs** : auto à l'ouverture de l'app **+** bouton manuel / pull-to-refresh.
5. **Cooldown différencié** : auto = 30 min (`1800s`), manuel = 5 min (`300s`).

## Architecture

```
App (ouverture auto / bouton manuel)
   │ JWT user
   ▼
Server Action  triggerGarminSync(trigger: "auto" | "manual")
   │ JWT user (Authorization: Bearer)
   ▼
Worker  POST /garmin/sync?trigger=auto|manual
   │
   ├─ [garde-fou] claim atomique sur garmin_credentials.last_sync_trigger_at
   │      ├─ refusé  → { status: "cooldown", retry_after_seconds, last_sync_at }
   │      └─ accordé → lance la sync en thread daemon, renvoie { status: "started" }
   │
   ▼ (thread daemon)
run_sync_for_user(user_id, mode=activities_only)  → DB upsert + recompute Banister
```

### Unités et responsabilités

| Unité | Rôle | Dépend de |
|---|---|---|
| `try_claim_sync()` (worker) | Claim atomique du créneau (check + log en un appel), renvoie `claimed` \| `cooldown` (+ `retry_after_seconds`) \| `no_credentials` | `garmin_credentials.last_sync_trigger_at`, service-role |
| `POST /garmin/sync` (worker `main.py`) | Endpoint user-facing : JWT → claim → spawn thread sync → réponse | `_require_user_jwt`, `try_claim_sync`, `run_sync_for_user` |
| `triggerGarminSync` (Server Action) | Relaie le JWT au worker, mappe la réponse pour l'UI | `lib/worker.ts`, session Supabase |
| Composant bouton + hook auto (front) | Bouton manuel (spinner/toast) + déclenchement auto au montage du layout `(app)` | Server Action |

## Détail du garde-fou

Nouvelle colonne sur `garmin_credentials` :

```sql
ALTER TABLE garmin_credentials
  ADD COLUMN IF NOT EXISTS last_sync_trigger_at timestamptz;
```

Claim atomique (exécuté par le worker en service-role) :

```sql
UPDATE garmin_credentials
SET last_sync_trigger_at = now()
WHERE user_id = :uid
  AND (last_sync_trigger_at IS NULL
       OR last_sync_trigger_at < now() - make_interval(secs => :window_seconds))
RETURNING last_sync_trigger_at;
```

- **Ligne renvoyée** → créneau réservé, on lance la sync.
- **Aucune ligne** → ambigu (cooldown actif **ou** pas de ligne credentials). Le worker
  fait un `SELECT last_sync_trigger_at FROM garmin_credentials WHERE user_id = :uid`
  pour désambiguïser :
  - ligne absente → `no_credentials` (l'utilisateur n'a pas connecté Garmin) ;
  - ligne présente → `cooldown`, avec
    `retry_after_seconds = window_seconds - (now - last_sync_trigger_at)`.
- **Atomicité** : le `WHERE ... RETURNING` fait check + claim en une seule requête → pas
  de race entre deux ouvertures simultanées.
- **On gate sur la tentative (claim), pas sur le succès** : un sync échoué ne permet pas
  de re-spammer Garmin immédiatement.
- **Une seule colonne pour les deux fenêtres** : un claim auto récent (≤30 min) bloque les
  auto suivants mais laisse passer un manuel après 5 min (`last_sync_trigger_at < now()-300s`).

`window_seconds` est dérivé du paramètre `trigger` côté worker (source de vérité serveur) :
`auto → 1800`, `manual → 300`. Toute autre valeur de `trigger` est rejetée (400).

## Endpoint worker

```
POST /garmin/sync?trigger=auto|manual
Authorization: Bearer <user_jwt>
```

- `_require_user_jwt(authorization)` → `user_id` (jamais lu du body/query).
- Valide `trigger ∈ {auto, manual}` (sinon 400).
- `outcome = try_claim_sync(user_id, window_seconds)` → `claimed` | `cooldown` | `no_credentials`.
  - `cooldown` → `{ "status": "cooldown", "retry_after_seconds": N, "last_sync_at": ... }`.
  - `no_credentials` → `{ "status": "no_credentials" }`.
- Si `claimed` → spawn `threading.Thread(target=run_sync_for_user,
  kwargs={"user_id": ..., "mode": SYNC_MODE_ACTIVITIES_ONLY}, daemon=True).start()`,
  puis `{ "status": "started" }`.
- Erreurs internes → pattern `error_id` existant (`{status, error_id, type}`), comme
  `/garmin/connect`.

Les statuts Garmin (`rate_limited`, `auth_failed`) restent gérés **dans** `run_sync_for_user`
et persistés sur `garmin_credentials.last_sync_status` ; ils ne remontent pas dans la
réponse HTTP (le thread est détaché). L'UI les lit via le statut de sync existant.

## Server Action

Nouveau fichier dédié `app/actions/garmin-sync.ts` :

```ts
triggerGarminSync(trigger: "auto" | "manual"):
  Promise<{ status: "started" | "cooldown" | "error"; retryAfterSeconds?: number }>
```

- Récupère le JWT de la session Supabase, appelle le worker via `lib/worker.ts`.
- Mappe la réponse worker → type UI ci-dessus.
- Ne throw pas pour un cooldown (cas nominal) ; ne throw pas non plus côté auto (silencieux).

## UX front

- **Auto à l'ouverture** : déclenchement fire-and-forget au montage du layout `app/(app)/`
  (composant client léger). Cooldown → **silencieux** (aucun message). Les données se
  rafraîchissent au prochain rendu / revalidation.
- **Bouton manuel / pull-to-refresh** : spinner pendant l'appel, puis toast :
  - `started` → « Synchronisation lancée ».
  - `cooldown` → « Déjà à jour — dernière synchro il y a X min » (utilise `last_sync_at`
    déjà exposé par `sync-timings-card`).
  - `error` → message générique + invitation à réessayer.
- Placement du bouton : à côté de l'affichage de fraîcheur existant (`sync-timings-card`).

## Gestion des erreurs

| Cas | Comportement |
|---|---|
| Cooldown (claim refusé) | Cas nominal, pas une erreur. `{status:"cooldown"}`, UI silencieuse (auto) ou informative (manuel). |
| JWT absent/invalide | 401 via `_require_user_jwt`. |
| `trigger` invalide | 400. |
| Pas de credentials Garmin | `try_claim_sync` détecte l'absence de ligne (SELECT) et renvoie `no_credentials` sans lancer de thread. L'UI auto reste silencieuse ; le bouton manuel peut inviter à connecter Garmin. |
| Rate-limit / auth Garmin | Géré et persisté dans `run_sync_for_user` ; visible via le statut de sync. |
| Crash endpoint | Pattern `error_id`, trace dans les logs worker. |

## Plan de tests

**Worker**
- `try_claim_sync` : premier appel accorde ; second dans la fenêtre refuse ; après expiration
  de la fenêtre accorde ; calcul de `retry_after_seconds`.
- Fenêtres différenciées : claim auto (1800s) puis manuel (300s) → manuel passe après 5 min,
  auto bloqué avant 30 min.
- Endpoint `/garmin/sync` : JWT requis (401) ; `trigger` invalide (400) ; cooldown
  (`{status:"cooldown"}` sans appel Garmin) ; accordé (`{status:"started"}`, thread lancé —
  mock de `run_sync_for_user`).

**Frontend**
- Server Action : mapping `started` / `cooldown` / `error`.
- Composant bouton : états spinner, toast started, toast cooldown.

## Hors scope (YAGNI)

- Pas de push temps réel (Strava webhooks = E15.1, Garmin officiel = E15.2).
- Pas de file d'attente / worker pool : un thread daemon suffit pour 1 owner + 5-10 amis.
- Pas de WebSocket / SSE de notification « sync terminée » : le rafraîchissement au rendu
  suffit pour le MVP.
- Pas de sync `full` on-demand : sleep/HRV/body restent au cron (pas le besoin « live »).

## Migrations

- `supabase/migrations/<timestamp>_garmin_sync_trigger_throttle.sql` :
  `ADD COLUMN last_sync_trigger_at timestamptz` sur `garmin_credentials`.
  (Auto-appliquée sur `main` via la CI E17.)

## Critères d'acceptation

1. Ouvrir l'app déclenche au plus une sync auto / 30 min par user.
2. Le bouton manuel déclenche au plus une sync / 5 min par user ; en cooldown il informe
   l'utilisateur sans appeler Garmin.
3. Deux ouvertures simultanées ne déclenchent qu'une seule sync (atomicité).
4. La sync on-demand est `activities_only` (delta 2 jours) et ne touche pas Garmin en cas
   de cooldown.
5. Tous les quality gates passent (lint, typecheck, tests, coverage, SonarQube).
