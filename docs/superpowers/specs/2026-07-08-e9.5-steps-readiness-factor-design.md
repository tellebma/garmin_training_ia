# E9.5 — Steps comme signal contextuel du briefing (readiness)

**Date** : 2026-07-08
**EPIC** : E9 — Cockpit de performance et suivi longitudinal
**Statut** : Spec validée (design approuvé)
**Priorité** : P2

## Contexte et objectif

Le worker synchronise déjà `totalSteps` (colonne `steps` de `daily_metrics`, voir
`transformers/daily.py`) mais cette donnée n'est utilisée nulle part dans le coaching.
Discussion avec l'owner : une journée avec beaucoup de marche/escaliers (NEAT — non-exercise
activity thermogenesis) représente une fatigue réelle qui n'apparaît dans aucune activité
Garmin structurée, donc dans aucun TSS/CTL/ATL (modèle Banister, E4). Elle est en partie
captée indirectement par `stress_avg` (dérivé de la HRV mesurée en continu par la montre),
mais pas explicitement.

Décision produit (issue du brainstorming) : ajouter `steps` comme **6ème signal de
récupération**, au même niveau que HRV/FC repos/sommeil/stress/Body Battery (E9.3), avec un
**poids volontairement faible** dans le `readiness_score` — la base scientifique reliant un
seuil de pas à un risque de fatigue chez un triathlète déjà entraîné est faible comparée à
HRV (tonus vagal, littérature établie) ou au sommeil. Le signal est donc traité comme un
indice indirect et secondaire, pas comme une mesure physiologique directe.

Explicitement **hors scope** : panneau `/stats` (`RecoveryPanel`), floors montés
(`floorsAscended`, non synchronisé), et toute garde anti-doublon avec `stress_avg` (le
poids réduit rend le risque de double comptage négligeable — cohérent avec le fait que les
5 signaux existants peuvent déjà se chevaucher partiellement sans garde-fou dédié).

## Décisions de design (validées)

1. **Réutilisation stricte du pattern E9.3** : `steps` devient une 6ème métrique dans
   `recovery_baselines.py`, calculée par `compute_metric_baseline` (déjà générique),
   `higher_is_better=False` (comme `stress`/`resting_hr` : plus haut que la baseline perso
   = signal de fatigue, pas de forme).
2. **Un nouveau facteur `_score_steps`** dans `briefing.py`, câblé comme `_score_stress`.
3. **Seuil** : `steps > baseline * 1.5` (vs `1.2` pour stress, `1.1` pour resting_hr) — les
   pas quotidiens varient naturellement plus d'un jour à l'autre qu'un score de stress ou
   une FC repos, un seuil plus large limite les faux positifs.
4. **Poids** : `-5` (échelle de référence : stress/resting_hr = -10, tsb_negative = -8,
   sleep_short = -5) — signal faible et indirect, ne fait jamais à lui seul basculer
   `ready` → `caution`.
5. Aucun changement de format de sortie JSON du briefing (rétrocompat) : `steps_high` est
   un `ReadinessFactor` de plus dans la liste `factors`, comme les autres.

## Architecture

```
Sync quotidien (cron.py, après recompute_daily_state)
        │
        ▼
recompute_recovery_baselines(user_id)        [recovery_baselines.py — inchangé, +1 métrique]
        │  lit daily_metrics(steps) sur 28 j, dans la même passe que resting_hr/stress
        ▼
  table recovery_baselines  (+colonne jsonb "steps")
        └─→ briefing.py : _score_steps(daily, rec.steps) → ReadinessFactor "steps_high" (-5)
```

Pas de nouveau flux de données : `steps` est déjà synchronisé quotidiennement dans
`daily_metrics` par le sync existant (E2). Seul le calcul de baseline et le facteur de
briefing sont nouveaux.

## Changements détaillés

### `recovery_baselines.py`

- `recompute_recovery_baselines` : ajouter `steps` à la sélection `daily_metrics`
  (`"date, resting_hr, stress_avg, body_battery_high, steps"`).
- Calculer `steps = compute_metric_baseline(_series(daily_rows, "steps"), today=today,
  higher_is_better=False)`.
- Ajouter `"steps": steps` à la ligne upsertée dans `recovery_baselines`.

### Table `recovery_baselines` (migration)

```sql
alter table public.recovery_baselines
  add column if not exists steps jsonb;
```

Migration auto-appliquée via la CI E17 au merge sur `main` (comme toutes les migrations du
projet). Colonne nullable : les lignes existantes restent valides sans backfill (le prochain
sync recalcule et remplit `steps`).

### `briefing.py`

- `_load_daily_metrics` : ajouter `steps` à la sélection.
- `_load_recovery_baselines` : ajouter `steps` à la sélection.
- `_RecoveryInputs` : ajouter un champ `steps: float | None`.
- `_resolve_recovery_baselines` : `steps=_gated_baseline(data.get("steps"))` (gate sur
  confidence `high`/`medium`, comme `stress` et `body_battery` — pas de repli sur seuil
  absolu si baseline non fiable, contrairement à `resting_hr` qui a un historique de repli
  dédié : ici, en l'absence de baseline fiable, le facteur ne se déclenche simplement pas).
- Nouvelle fonction, à côté de `_score_stress` :

```python
def _score_steps(daily: dict[str, Any] | None, baseline: float | None) -> list[ReadinessFactor]:
    if not daily or not baseline or baseline <= 0:
        return []
    steps = daily.get("steps")
    if steps is None:
        return []
    if steps > baseline * 1.5:
        return [
            ReadinessFactor(
                "steps_high", -5, f"Beaucoup de pas hier ({steps} vs médiane {baseline:.0f})."
            )
        ]
    return []
```

- `compute_briefing` : ajouter `factors.extend(_score_steps(daily, rec.steps))`, à la suite
  de `_score_stress` (même famille de signal, ordre d'affichage cohérent dans
  `explanation_md`).

## Gestion des erreurs

| Cas | Comportement |
|---|---|
| Pas de `daily_metrics` pour hier | `_score_steps` retourne `[]` (pas de facteur, pas d'exception) — identique aux autres facteurs. |
| Baseline `steps` absente ou confiance `low`/`no_data` | Facteur non déclenché (gate via `_gated_baseline`), comme `stress`. |
| Colonne `steps` absente en base (avant migration) | Non applicable après merge : la migration s'applique avant tout déploiement du code qui la lit (ordre CI existant). |
| Échec de `recompute_recovery_baselines` | Déjà avalé et loggé (comportement existant, inchangé). |

## Plan de tests

**`recovery_baselines.py`** (`test_recovery_baselines.py`)
- `recompute_recovery_baselines` upsert désormais 6 métriques dont `steps` (DB mockée avec
  des lignes `daily_metrics` incluant `steps`).
- Réutilise `compute_metric_baseline` déjà testé : pas de nouveau test unitaire nécessaire
  pour la mécanique de médiane/tendance/confiance (couverte par les tests HRV/resting_hr
  existants, `higher_is_better=False` déjà exercé par `resting_hr`/`stress`).

**`briefing.py`** (`test_briefing.py`)
- `_score_steps` : pas de données → `[]` ; steps sous le seuil (`<= baseline * 1.5`) →
  `[]` ; steps au-dessus du seuil → un `ReadinessFactor("steps_high", -5, ...)` ; baseline
  `None`/`0` → `[]`.
- `compute_briefing` : cas de référence existant non cassé (format de sortie JSON
  inchangé) ; nouveau cas avec steps élevés → `steps_high` apparaît dans `factors` et
  `explanation_md`, `readiness_score` diminué de 5 par rapport au même cas sans le facteur.

## Hors scope (YAGNI)

- Pas d'affichage dans `/stats` (`RecoveryPanel`) : le signal reste interne au briefing.
- Pas de synchronisation de `floorsAscended` (étages montés) : steps seul, donnée déjà
  disponible.
- Pas de garde anti-doublon avec `stress_avg` : poids réduit (-5) jugé suffisant pour
  limiter l'impact d'un éventuel chevauchement.
- Pas de repli sur seuil absolu façon `resting_hr` (30 j médiane hors baselines) : en
  l'absence de baseline personnelle fiable, le facteur ne se déclenche pas, point.

## Critères d'acceptation

1. Après un sync, `recovery_baselines.steps` est renseigné (ou `no_data` si historique
   insuffisant), au même titre que les 5 métriques existantes.
2. Un jour où `steps` dépasse 1.5× la médiane personnelle 28 j (baseline confiance
   `high`/`medium`), le briefing inclut un facteur `steps_high` d'impact `-5` et une
   ligne explicative dans `explanation_md`.
3. En l'absence de baseline fiable ou de donnée du jour, aucun facteur n'est ajouté (pas
   d'exception, pas de faux signal).
4. Le format de sortie JSON du briefing (`DailyBriefing`) reste inchangé pour les
   consommateurs existants (`/today`).
5. Tous les quality gates passent (worker pytest/ruff/mypy, migration appliquée en CI,
   SonarQube, coverage).
