# Spec — E14.1 Graphiques pro (analyse d'activité niveau Garmin/Strava)

- **Date** : 2026-06-27
- **EPIC** : E14 — Visualisation pro et pédagogie des métriques
- **Statut** : validé en brainstorming, prêt pour plan d'implémentation
- **Auteur** : owner + Claude

## Contexte

La page détail d'activité (`app/(app)/history/[id]/page.tsx`) affiche aujourd'hui :
- un **graphe unique multi-lignes** (`ActivitySamplesChart`, recharts `LineChart`) où FC, altitude,
  puissance, cadence et allure sont superposées sur un seul axe Y — illisible dès que les échelles
  divergent ;
- une section **« Zones cardio »** textuelle alimentée par `summarizeActivitySamples` (qui produit
  déjà `HeartRateZoneSummary[]`) ;
- la **trace GPS** (`ActivityRouteMapLazy`, livrable B carto) avec trace colorée par métrique.

Les données sont dans `activity_samples` (`elapsed_s`, `distance_m`, `elevation_m`, `heart_rate_bpm`,
`power_w`, `cadence_rpm`, `speed_m_s`, `latitude`, `longitude`). Tout ce que demande E14.1 est
**dérivable de ces samples** — aucune migration, aucun travail worker.

## Objectif

Élever l'analyse d'activité au niveau Garmin/Strava :

1. **Graphes séparés par métrique** (altitude, FC, allure/vitesse, puissance, cadence), lisibles,
   chacun avec sa propre échelle, alignés sur un axe temps/distance commun.
2. **Survol synchronisé** : un curseur vertical commun à tous les graphes affiche les valeurs au même
   instant, **et** un marqueur sur la carte GPS pointe le tronçon correspondant.
3. **Zones FC** : distribution visuelle (barres) du temps par zone.
4. **Splits par km** : tableau allure / FC / D+ par kilomètre, dérivé des samples.
5. **Distribution d'effort** : temps passé par zone d'allure (course) ou de puissance (vélo).

## Décisions validées

| Sujet | Décision | Raison |
|---|---|---|
| Source de données | `activity_samples` uniquement (+ zones FC déjà calculées) | Aucune migration ni worker ; les laps Garmin ne sont pas stockés, les splits sont recalculés par km depuis les samples. |
| Librairie graphes | **recharts** (déjà utilisée) | Cohérence avec l'existant ; `ReferenceLine` pour le curseur partagé. |
| Survol synchronisé | État `hoveredIndex` remonté dans un conteneur client `ActivityDetailViz` | Un seul état partagé entre N graphes + la carte ; pas de couplage direct entre composants. |
| Couplage carte | La carte reçoit `hoveredIndex` et affiche un marqueur MapLibre au point GPS | Corrélation tronçon ↔ FC/allure, cœur de l'expérience Strava. |
| Découpage | 2 livrables séquentiels (A graphes synchronisés, B agrégats) | Chacun = un plan / une PR, livrable indépendamment. |

## Architecture

### Conteneur de survol partagé

Nouveau composant client `app/(app)/_components/activity/activity-detail-viz.tsx` :
- Détient `const [hoveredIndex, setHoveredIndex] = useState<number | null>(null)`.
- Rend les graphes empilés + la carte, leur passe `hoveredIndex` et un `onHover(index | null)`.
- `hoveredIndex` est un **index de sample** (pas une coordonnée pixel) — chaque graphe et la carte le
  résolvent vers leur propre représentation.

Remplace, sur la page détail, l'actuel bloc `ActivitySamplesChart` + carte par ce conteneur (la page
reste un Server Component qui charge les samples et les passe au conteneur client).

### Graphes par métrique

Dans `app/(app)/_components/charts/` (à côté des graphes existants), un composant par métrique,
chacun masqué si la métrique est absente des samples :
- `AltitudeProfileChart` (recharts `AreaChart`),
- `HeartRateChart`, `PaceChart`, `PowerChart`, `CadenceChart` (`LineChart`).

Contrat commun (interface partagée `SyncedChartProps`) :
```ts
interface SyncedChartProps {
  readonly samples: ActivitySample[]
  readonly hoveredIndex: number | null
  readonly onHover: (index: number | null) => void
  readonly xKey: 'elapsed_s' | 'distance_m'
}
```
- Axe X commun (`xKey`), curseur via `<ReferenceLine x={...} />` piloté par `hoveredIndex`.
- `onMouseMove`/`onMouseLeave` de recharts → `onHover(activeTooltipIndex | null)`.
- Tooltip soigné réutilisant les tokens dark existants.

### Carte corrélée

Étendre `ActivityRouteMap` (livrable B) pour accepter `hoveredIndex` et `onHover` optionnels :
- Au changement de `hoveredIndex`, déplacer/afficher un marqueur MapLibre au sample `[lng, lat]`
  correspondant (no-op si le sample n'a pas de GPS).
- Au survol de la trace sur la carte (optionnel, si peu coûteux), remonter `onHover`.
- Rétrocompat : sans ces props, le composant se comporte comme aujourd'hui.

### Lib d'analyse (utils purs, testés)

Étendre `lib/coach/activity-analysis.ts` (ou nouveau module `lib/activity/derived.ts`) :
- `computeKmSplits(samples): KmSplit[]` — découpe par tranche de 1000 m de `distance_m`, calcule pour
  chaque km : allure moyenne (s/km), FC moyenne, D+ (somme des deltas positifs d'`elevation_m`).
  Type `KmSplit { km: number; durationS: number; paceSPerKm: number | null; hrAvg: number | null; elevGainM: number }`.
- `computeEffortDistribution(samples, metric): EffortBucket[]` — temps passé par bucket d'allure ou de
  puissance. Type `EffortBucket { label: string; samples: number; percent: number }`.
- Les zones FC restent fournies par `summarizeActivitySamples` existant.

### Composants agrégats (livrable B)

- `HrZonesChart` — barres horizontales depuis `HeartRateZoneSummary[]` (remplace la liste textuelle
  actuelle ou la complète).
- `SplitsTable` — tableau des `KmSplit[]` (km, allure, FC, D+), responsive.
- `EffortDistributionChart` — barres depuis `EffortBucket[]`.

## Découpage en livrables

- **Livrable A — Graphes synchronisés** : `ActivityDetailViz` + graphes par métrique + curseur de
  survol partagé + marqueur corrélé sur la carte. À la fin, le détail affiche des graphes pro
  lisibles avec survol synchronisé graphes ↔ carte.
- **Livrable B — Agrégats** : `computeKmSplits`, `computeEffortDistribution`, `HrZonesChart`,
  `SplitsTable`, `EffortDistributionChart`.

## Accessibilité

Leçon S6819 (livrable B) retenue : les graphes/canvas ne sont **pas** accessibles aux lecteurs
d'écran. Chaque bloc visuel est `aria-hidden` et accompagné d'une **alternative texte** (`sr-only` ou
résumé déjà présent, ex. la liste des zones cardio). **Ne jamais** utiliser `role="img"` (déclenche
S6819). Les tableaux (`SplitsTable`) sont du vrai HTML `<table>` accessible.

## Tests

- **Utils purs (vitest)** : `computeKmSplits` (tranches de 1 km, dernier km partiel, samples sans
  distance, D+ ne compte que les deltas positifs) ; `computeEffortDistribution` (buckets, pourcentages,
  métrique absente → vide).
- **Composants (vitest + mock recharts/maplibre)** : un graphe rend les bonnes séries et appelle
  `onHover` ; le conteneur `ActivityDetailViz` propage `hoveredIndex` aux enfants ; la carte place un
  marqueur au bon sample.
- **Quality gate SonarQube** : couverture du nouveau code ≥ 90 %, 0 violation (vérifier a11y), 0
  duplication > 3 %. Interroger l'API gate (`api/qualitygates/project_status?...&branch=main`, token
  `SONAR_TOKEN_TELLEBMA`) en cas d'échec pour lire la condition exacte.

## Hors périmètre (YAGNI)

- Récupération des **vrais laps Garmin** (endpoint worker dédié) — les splits par km dérivés suffisent
  pour le MVP.
- Courbe de puissance critique / records de puissance.
- Comparaison multi-activités sur les mêmes graphes (déjà couvert ailleurs par `activity-comparison-chart`).
- Zoom/sélection de plage sur les graphes.

## Critères de succès

1. Le détail d'activité affiche des graphes séparés et lisibles (altitude, FC, allure, puissance,
   cadence) selon les métriques disponibles.
2. Survol d'un graphe → curseur synchronisé sur tous les graphes **et** marqueur au bon point sur la
   carte.
3. Zones FC en barres, splits par km en tableau, distribution d'effort en barres.
4. Tout dégrade proprement quand une métrique ou le GPS manque.
5. Quality gates verts (lint, typecheck, tests, build, Sonar : couverture + 0 violation).
