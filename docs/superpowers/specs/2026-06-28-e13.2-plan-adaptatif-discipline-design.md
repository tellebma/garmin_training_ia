## Gaps restants

### Gap A — Le niveau effectif n'est pas utilisé dans les régénérations

`coach/sessions.py::_load_profile_and_race` ne lit que `sports_strengths` **déclarés** et passe
l'`athlete` tel quel au LLM. Une séance **régénérée / générée à la demande** n'a donc pas la même
calibration par discipline que le plan (qui, lui, utilise l'effectif). Le BACKLOG demandait
explicitement de brancher le niveau sur « planner + prompt LLM + **ajustements** ».

### Gap B — La progression n'est pas différenciée par discipline

`_ramp_rate_for_week` est **global** (+5 %/sem, deload toutes les 4 sem, taper) et identique aux
trois disciplines. Le biais vers les disciplines faibles est **statique** (même +25 % de part
chaque semaine). Le BACKLOG veut « investir davantage sur les disciplines faibles sans surcharge »
et des « garde-fous progression run ».

## Conception

### Architecture — helper partagé (DRY)

Le planner recalcule l'effectif inline. On extrait un helper réutilisé par planner **et**
sessions :

```python
# coach/discipline_level.py (ajout)
def load_effective_strengths(db: Any, user_id: str, today: date | None = None) -> dict[str, int]:
    """Charge sports_strengths déclarés + activités 90j → niveaux effectifs par discipline."""
```

- Charge `athlete_profiles.sports_strengths` (défaut `{"swim":3,"bike":3,"run":3}`).
- Charge les activités sur `WINDOW_DAYS` (90j) — mêmes colonnes que le planner
  (`start_time, sport, duration_s, tss`).
- Retourne `compute_discipline_levels(declared, activities, today).effective_strengths`.

`generate_plan` est refactoré pour appeler ce helper (supprime sa duplication).

### Gap A — Injecter l'effectif dans `sessions.py`

Dans `_load_profile_and_race` (ou juste après, avant génération), appeler
`load_effective_strengths(db, user_id)` et **remplacer** `athlete["sports_strengths"]` par les
valeurs effectives. Le prompt (`_athlete_lines`) reflète alors le niveau effectif et la consigne
« disciplines faibles » devient cohérente avec le plan. **Aucun changement de signature** du
prompt.

### Gap B1 — Biais progressif (`distribute_weekly_tss_by_sport`)

La fonction gagne un paramètre `progress: float` (∈ [0,1]) modulant l'**amplitude** du biais :

```
boost(score)      = 0.25 - (score - 1) * 0.10      # niveau 1 → +0.25, 3 → 0, 5 → -0.15
weight(score, p)  = 1.0 + boost(score) * bias_curve(p)
```

- `bias_curve(p)` croît de **0.5** (début) à **1.0** (fin de build), puis **tenue à 1.0** en
  peak/taper. Concrètement : `bias_curve(p) = 0.5 + 0.5 * clamp(p, 0, 1)`.
- `progress` est dérivé du déroulé du plan dans le planner : `p = 0` au début de la base, `p = 1`
  à la fin de la phase build (puis tenu). Calcul : `p = clamp(week_offset / max(1, last_build_week_offset), 0, 1)`,
  où `last_build_week_offset` est l'index de la dernière semaine de build.
- Les poids restent **normalisés** pour que la somme = `weekly_tss` (comportement actuel conservé).
- Rétro-compatibilité : `progress` a une valeur par défaut `1.0` → comportement statique actuel
  (biais plein) si un appelant ne le fournit pas.

Effet : volume équilibré tôt, investissement croissant sur les disciplines faibles vers la fin du
build, stabilisé avant la course.

### Gap B2 — Garde-fou de hausse hebdo par discipline

Après distribution du TSS par sport pour une semaine, **plafonner l'augmentation** vs la semaine
précédente, par sport :

```python
WEEKLY_RAMP_CAP = {"run": 1.10, "swim": 1.15, "bike": 1.20}  # +10 % / +15 % / +20 %
```

- Pour chaque sport : `tss_capped = min(tss_distributed, prev_week_tss[sport] * cap[sport])`.
- **Uniquement les hausses** sont bridées : si `tss_distributed <= prev`, aucun changement
  (deload, taper, baisses jamais bridés).
- L'excédent retiré **n'est pas redistribué** vers les autres sports (sécurité avant volume) →
  le total de la semaine peut passer légèrement sous le ramp global ; comportement assumé.
- Première semaine (pas de précédent) ou sport absent la semaine précédente : **pas de cap**
  (rien à comparer).
- Implémentation dans la boucle de construction hebdomadaire du planner (`_build_week_sessions` /
  `_compute_tss_by_date`), en mémorisant le TSS par sport de la semaine précédente.

progression/stagnation à partir des données réalisées. Complémentaires ; pas de logique dupliquée.

## Critères d'acceptation

1. Une **régénération / génération à la demande** de séance reflète le niveau **effectif**
   (reconcilié 90j), pas le déclaré brut.
2. À TSS hebdo égal, une discipline faible reçoit une part de volume **strictement plus élevée**
   en fin de build qu'en début de base (biais progressif).
3. Le TSS **course** n'augmente jamais de plus de **+10 %** d'une semaine à l'autre (hors deload /
   taper, qui réduisent).
4. Les **baisses** de charge (deload, taper) ne sont jamais bridées par le garde-fou.
5. Tout reste **borné** : niveau effectif ±1, parts normalisées à `weekly_tss`, `progress` clampé
   [0,1].
6. Aucun changement de schéma DB ni de frontend ; les 37 tests existants restent verts.
